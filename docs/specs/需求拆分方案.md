## 拆分总览

原编制日期：2026-10-11；规则更新：2026-10-17。页面流程与业务提交的验收边界已由用户确认；下方列出的业务待确认项继续保留。

### 依据与优先级

1. 用户最新决定：正式前端采用 React，以 Vite 为前端开发与构建基座；后端采用 Next.js；数据库采用 PostgreSQL。管理员系统与员工系统采用 Monorepo，正式前端分别放在 `apps/admin` 和 `apps/employee`，共用后端放在 `apps/api`。
2. 前端页面以当前《仓库管理系统_双击打开.html》为准：入口、导航、布局、字段、按钮、弹窗及手机交互沿用 Demo。Demo 继续保持原生 HTML、CSS、JavaScript，不因正式项目的技术选型而改写。
3. 《需求设计.md》规定正式系统的库存规则、账号边界、数据保存、Excel 核对和验收要求。Demo 中的模拟数据、固定密码、刷新复原等行为只用于演示。
4. 《GLOSSARY.md》及“库存保留实际整件与散个状态”ADR 规定业务术语和包装数量规则。未确认项见 [Demo 差异与待确认](#demo-differences)。

前端发生冲突时保留 Demo 的现有页面和控件，把文档中超出 Demo 的交互列为待确认；正式系统的数据完整性与权限要求不因 Demo 没有后端而取消。

### 拆分清单

每份规格围绕一个可验收的业务结果，后续可据此拆实施任务。本次尚未创建任务或实现正式系统。

| 编号 | 规格 | 员工系统 | 管理员系统 | 依赖 | 主要验收结果 |
| --- | --- | --- | --- | --- | --- |
| S01 | [独立登录与双端页面](#s01) | 独立员工入口、登录、导航 | 独立管理员入口、登录、导航 | S09 数据基础 | 跨系统账号与会话被拒绝，电脑手机入口正确 |
| S02 | [产品规格与货位维护](#s02) | 新增产品及包装规格、新增货位 | 同样功能 | S01、S09 数据基础 | 按名称、规格、材质、颜色识别产品；不同每件个数分别记账并归组展示 |
| S03 | [共享库存查询](#s03) | 查询与展开货位 | 同样功能 | S01、S02、S09 | 两端读到同一库存，整件与散个分别汇总 |
| S04 | [入库出库移位拆件](#s04) | 四种业务、首次手工入库 | 同样功能 | S01、S02、S03、S09 | 库存校验、变动、流水同时成功或失败 |
| S05 | [业务历史与记录更正](#s05) | 跨操作人查询与更正 | 同样功能 | S03、S04、S09 | 更正影响正确，前后内容和修改人可追溯 |
| S06 | [员工账号管理](#s06) | 无管理入口 | 新增、启用、停用员工账号 | S01、S09 | 员工不能调用管理功能，停用账号不能继续办理 |
| S07 | [初始库存Excel导入](#s07) | 无导入入口；手工录入使用入库 | 预览并持续分批导入 | S01、S02、S04、S09 | 支持 .xlsx、.xls、.csv；新批次叠加；问题行修正源文件后重传 |
| S08 | [系统操作日志](#s08) | 仅查询员工端日志 | 查询两端日志并筛选 | S01；接收 S02、S04、S05、S06、S07 操作 | 管理员能看到员工办理业务的账号、内容、来源和时间 |
| S09 | [共享持久化并发与运行保障](#s09) | 所有业务共同使用 | 所有业务共同使用 | 为其他规格提供数据基础；最终验收依赖全部模块 | PostgreSQL 持久保存、并发不透支、重试不重复、备份可恢复 |

S09 的数据基础先实施，最终并发、恢复及外网验收最后完成；不能把它当成所有其他模块完成后才开始的数据库任务。S04 负责业务数量规则，S05 负责更正规则，S09 负责保证它们在真实存储和并发下成立，避免重复建设。

### Demo 页面与表单契约

| 页面或弹窗 | 现有字段 / 控件 | 正式实现边界 |
| --- | --- | --- |
| 库存查询 | 关键词；仓库筛选；产品与规格、每件个数、货位数量、整件与散个；展开明细 | 保留表格与手机可展开列表，不新增统计看板 |

| 移位 | 产品规格、原货位、目标货位、整件数、散个数、实际发生时间、备注 | 没有第二货位时提示先新增货位；两个货位原子更新 |
| 拆件 | 产品规格、货位、拆开件数、转换预览、实际发生时间、备注 | 固定每件个数计算增加散个，不自动折回整件 |
| 业务历史 | 类型按钮组、关键词、来源系统；类型、产品规格、变动、货位、实际时间、登记时间、操作人 / 来源 | 不添加独立日期、货位或操作人选择框；超出 Demo 的筛选见差异表 |
| 更正记录 | 原记录摘要；整件 / 散个或拆开件数、实际发生时间、备注 | 本轮表单保留这些字段；规格和货位更正另列待确认 |
| 修改记录 | 修改人、来源系统、修改时间、修改前与修改后内容 | 使用查看弹窗，不提供删除历史按钮 |

| 新增货位 | 产品规格、仓库、货位名称 | 新货位对应库存为零 |
| 员工账号 / 新增账号 | 姓名、账号、状态、创建日期、启停操作；新增姓名和账号 | 正式密码建立方式需确认，不采用 Demo 固定密码 |

### 技术与模块边界

- `apps/admin` 和 `apps/employee` 分别采用 React＋Vite，负责各自系统的页面、表单、列表、请求状态与反馈。按 Demo 重建 React 组件，不在当前静态原型上安装或迁移正式应用。
- `apps/api` 运行 Next.js，使用 HTTP 请求处理入口承接两端的登录、查询和业务提交。三个应用必须处于同一仓库；两个前端分别由 Vite 构建，后端使用 Next.js 自身构建过程，构建产物和运行边界各自明确。
- PostgreSQL 是正式系统和数据库集成测试的数据来源。本轮不规划 SQLite 分支。
- 浏览器不直接连接数据库；身份、来源系统、权限、库存校验、事务及重试识别在后端执行。来源系统与操作账号由可信会话确定，不能任由请求正文指定。
- 数据至少覆盖账号及系统身份、会话、产品规格、仓库货位、规格货位库存、业务记录、修改记录、初始化状态、导入批次及系统日志。技术主键、迁移方式、ORM、精确 HTTP 地址和索引在实施时确定。
- 业务提交统一表达成功、字段错误、库存不足、权限拒绝、状态冲突和可重试失败。各模块规定可观察结果，不把存储细节泄露成页面术语。
- 前后端按同一业务契约工作；一次成功提交能关联库存、业务记录和必要系统日志。幂等规则见 S09。

以上是根据用户选型形成的架构拆分。Next.js 请求处理能力和构建命令、Vite 的 React 基座见 [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)、[Next.js CLI](https://nextjs.org/docs/app/api-reference/cli/next)、[Vite 官方指南](https://vite.dev/guide/)。

#### 两套系统各自包含的功能

| 代码位置 | 功能范围 | 系统边界 |
| --- | --- | --- |
| `apps/admin` | 管理员登录与退出；库存查询；入库、出库、移动货位、拆件；产品与货位；业务历史与更正；员工账号；持续分批的初始库存 Excel 导入；两端操作日志 | 有完整的管理员应用入口和导航。账号管理、Excel 导入只在这里实现；管理员日志可按员工／管理员来源筛选 |
| `apps/employee` | 员工登录与退出；库存查询；入库、出库、移动货位、拆件；产品与货位；业务历史与更正；员工系统操作日志 | 有完整的员工应用入口和导航。不包含员工账号管理和 Excel 导入页面；日志范围限员工系统 |

#### 复用与依赖规则

- 两端的调用方向为 `apps/admin`／`apps/employee` → HTTP → `apps/api` → PostgreSQL。共用一份产品规格、货位、库存和业务记录；日志保留可信的来源系统与操作账号。
- 两端相同的业务接口在各自路由完成身份校验后，调用后端同一个对应业务模块，不复制两套库存计算、事务或数据库表。
- `packages/ui` 只承接已经发生复用的展示组件和样式，不承接管理员专有业务、路由或会话。业务页面仍由各自应用组织。
- `packages/contracts` 只存放浏览器可使用的接口与字段契约，不放数据库连接、凭据、后端权限判断或库存事务。
- `apps/admin` 与 `apps/employee` 不相互导入；共享包不反向依赖应用。账号管理和 Excel 导入仍属于管理员应用及后端对应模块。
- 管理员与员工的登录入口及会话校验范围独立。共用后端不意味着两端会话可互换；同一浏览器打开两端时不能混用身份，来源不能由前端任意指定。
- 延续项目已有 npm 工具链，根 `package.json` 的 workspaces 管理 `apps/*` 和 `packages/*`，正式应用使用根锁文件。`prototype` 保持独立的静态原型用途，不作为正式 workspace 应用迁移。
- 根任务入口调用各应用自己的开发、构建和验收命令；管理员、员工前端分别产生构建结果，Next.js 后端独立构建。暂不增加额外任务编排工具，也不预设生产域名、端口或部署平台。
- 系统入口选择沿用 Demo，作为两端可到达的入口导航；选择员工或管理员后进入对应前端登录页，不再为入口选择单独创建第四个应用。

#### 规格落到代码的位置

- S01：两端各自的 `src/app`、`features/auth`，以及后端 `modules/auth` 和对应系统认证入口。
- S02：两端 `features/catalog` 与后端 `modules/catalog`；S03、S04：两端 `features/inventory` 与后端 `modules/inventory`；S05：两端 `features/records` 与后端 `modules/records`。
- S06：仅管理员 `features/accounts`，配合后端 `modules/accounts`；S07：仅管理员 `features/imports`，配合后端 `modules/imports`。

## S01 独立登录与双端页面

### Problem Statement

员工和管理员需要分别进入各自系统。只有隐藏管理按钮，不能保证员工账号无法登录管理员系统；从手机使用时，也需要完整且清楚的导航。

### Solution

按静态 Demo 建立系统入口、两个独立登录页及登录后的页面壳。正式前端在同一 Monorepo 的 `apps/admin`、`apps/employee` 分别采用 React＋Vite，后端在 `apps/api` 采用 Next.js 校验身份和会话，保留管理员系统与员工系统的独立边界。

### User Stories

1. 作为员工，我希望在系统入口选择员工系统，以便进入明确的员工登录页。
2. 作为管理员，我希望选择管理员系统，以便使用独立的管理员身份登录。
3. 作为员工，我希望员工账号不能登录管理员系统，以便账号的系统范围清晰。
4. 作为管理员，我希望管理员账号不被当成员工身份使用，以便业务来源能正确记录。
5. 作为使用者，我希望错误账号、密码或停用状态有明确提示，以便知道登录未成功。
6. 作为使用者，我希望登录后直接看到库存查询，以便开始日常工作。
7. 作为员工，我希望导航只列员工功能，以便不误进入账号管理和 Excel 导入。
8. 作为管理员，我希望导航包含员工账号、初始库存导入和两端日志，以便完成管理工作。
9. 作为手机使用者，我希望菜单能打开、关闭并在选页后收起，以便有足够空间查看库存。
10. 作为电脑使用者，我希望保留侧边导航、当前位置和当前账号，以便知道正在使用哪个系统。
11. 作为使用者，我希望退出后结束当前系统会话，以便账号不会留在其他人可继续使用的状态。
12. 作为使用者，我希望会话失效时清楚知道需要重新登录，以便不把未提交操作当成成功。

### Implementation Decisions

- 范围为入口、身份认证、会话、系统导航、手机菜单及通用页面状态。账号新增启停由 S06 承接。
- 两种系统身份分别认证；API 从会话取得账号和来源系统，不能接受客户端自报的角色作为权限依据。
- 管理员和员工分别拥有前端入口、路由、登录页及构建产物；各自调用后端对应系统的认证入口。共享展示组件不合并两端导航，也不引入管理员专有页面到员工应用。
- 页面顺序、登录字段、侧边栏及移动抽屉遵循 Demo；不新增注册、找回密码、第三种角色或新的首页看板。
- 会话失效统一表达为未登录状态；原表单输入在页面仍存在时保留，不将失败显示为成功。
- 密码使用不可逆安全存储方式；浏览器不能持有数据库凭据。正式系统不使用 Demo 固定密码。
- 首个管理员建立方式仍待确认；员工初始凭据按 Q02 使用一次性临时密码并在首次登录时强制修改，不将硬编码示例账号迁移到正式库。

### Testing Decisions

- 以页面登录完整流程和后端身份边界测试；复用 Demo 独立登录与手机菜单的交互先例。
- 员工账号调用管理员功能必须失败；管理员会话不能作为员工端会话直接使用。
- 两个前端可分别构建并打开各自登录页；同一浏览器同时打开管理员与员工应用时，会话身份及业务来源仍正确，不发生跨端身份串用。
- 错误密码、停用账号、未登录及失效会话都不能办理业务；退出后重用原会话不能继续提交。
- 桌面导航和手机抽屉显示与系统范围相符，手机选页后收起菜单，关闭弹窗和键盘操作可用。
- 验证 React 正式页面的入口、字段及层级与 Demo 一致，不以组件内部结构作为验收标准。

### Out of Scope

自助注册、社交登录、找回密码、多级角色体系和 React 改写当前双击 Demo。

### Further Notes

依赖 S09 数据基础；S06 负责员工账号生命周期，S08 接收登录与退出日志。首个管理员和密码建立方式见待确认清单。正式系统会话不能由纯静态 Demo 的内存状态证明。

## S02 产品规格与货位维护

### Problem Statement

同名产品可能有不同规格和包装数量，同一规格也可能分放多个货位。类别字段混合、直接修改已有每件个数或重复建立同一货位，都会让库存含义不清楚。

### Solution

两套系统使用共同的产品与货位资料，沿用 Demo 的列表、新增产品规格弹窗和新增货位弹窗。产品身份由产品名称、规格、材质和颜色确定；同一产品下不同每件个数分别作为包装规格记账，产品库归组展示。新货位从零库存开始。

### User Stories

1. 作为员工，我希望查看按产品身份归组的产品及其每件个数，以便选择正确的库存包装规格。
2. 作为管理员，我希望看到员工维护的同一套资料，以便双方不会各建一份产品表。
3. 作为员工，我希望新增产品时填写产品名称、规格、材质和颜色，以便正确识别产品身份。
4. 作为使用者，我希望每件个数能选择 2、4、6，以便符合已确认的包装规格。
5. 作为使用者，我希望商品类别、类别名称与备注分别保存，以便旧台账信息不会互相覆盖。
6. 作为使用者，我希望新增规格时指定仓库和首个货位，以便有明确存放位置。
7. 作为使用者，我希望为现有规格增加货位，以便支持分放。
8. 作为使用者，我希望新货位从 0 件 0 个开始，以便通过入库登记实际数量。
9. 作为使用者，我希望同一规格下相同仓库货位重复时有提示，以便避免重复建账。
10. 作为使用者，我希望同一产品可以建立不同每件个数的包装规格，以便各自记账又能在产品库归组查看。
11. 作为使用者，我希望输入中的特殊字符按文字显示，以便产品信息不破坏页面。
12. 作为使用者，我希望失败提交保留输入，以便修正后继续保存。

### Implementation Decisions

- 使用稳定身份关联产品规格、仓库和货位；库存以规格及货位组合定位。名称用于展示，不能成为历史关联的唯一依据。
- 资料展示和新增字段以 Demo 为准。产品名称、规格、仓库和货位需有值；类别与备注暂保持 Demo 的可空行为，最终必填规则仍待确认。
- 产品身份由产品名称、规格、材质和颜色确定；每件个数不是身份的一部分。同一产品可有多个包装规格，各包装规格分别维护货位库存。
- 已有库存或业务记录的包装规格不能原地改每件个数；新增的每件个数作为同一产品下的另一包装规格。遵循包装状态 ADR。
- 商品类别、类别名称和备注不参与产品身份；其业务含义及必填规则仍待确认。产品身份字段的必填规则和空值身份判定仍待确认。
- 资料维护成功产生系统操作日志；新增资料不直接产生库存数量。
- Demo 没有已有资料编辑、重命名或删除弹窗；本轮不擅自增加控件。文档中的名称修改要求保留为差异项。

### Testing Decisions

- 复用新增规格、独立类别字段、输入转义及新增货位的页面流程先例。
- 从员工端新增后，管理员端查询能看到相同资料；重启后仍存在。
- 新货位库存为零；同一产品包装规格的重复货位不能创建第二条记录。
- 同一产品身份的每件 4 个和每件 6 个分别记账，并在产品库归组；包装数量改变不改写已有业务记录。
- 产品名称和类别等输入含 HTML 字符时按普通文字显示。
- 产品身份规则已确认；空值是否可用及空值如何识别仍待确认，不能自行设定必填或空值合并规则。

### Out of Scope

产品图片、价格、采购销售资料、层级分类推断、删除有历史引用的资料，以及未经确认的资料编辑页面。

### Further Notes

依赖 S01 和 S09；供 S03、S04、S07 使用。产品身份字段的必填与空值规则、名称修改交互见 [Demo 差异与待确认](#demo-differences)。

## S03 共享库存查询

### Problem Statement

人员需要快速知道每个产品规格有多少整件和散个、分布在哪些货位。只显示折算总个数，或两个系统各有一份数据，都会影响现场判断。

### Solution

沿用 Demo 库存首页、关键词及仓库筛选、展开货位明细和业务操作入口。两套系统查询同一份 PostgreSQL 库存，电脑显示表格，手机显示可展开的列表。

### User Stories

1. 作为员工，我希望登录后看到全部产品规格库存，以便日常查询。
2. 作为管理员，我希望与员工看到同一份最新库存，以便进行管理核对。
3. 作为使用者，我希望按名称、规格或货位关键词查询，以便找到库存对象。
4. 作为使用者，我希望按仓库筛选，以便缩小库存位置范围。
5. 作为使用者，我希望同时看到整件和散个，以便知道真实包装状态。
6. 作为使用者，我希望跨货位分别汇总件数与散个，以便看到规格总量。
7. 作为使用者，我希望展开规格看到各货位数量，以便选对业务位置。
8. 作为使用者，我希望查看每件个数，以便理解拆件结果。
9. 作为使用者，我希望从货位直接办理入库或出库，以便减少重复选择。
10. 作为使用者，我希望从顶部进入移位和拆件，以便完成日常整理。
11. 作为手机使用者，我希望在窄屏展开明细和点击业务入口，以便外出查看。
12. 作为使用者，我希望无结果或查询失败时有明确反馈，以便不把失败当成零库存。

### Implementation Decisions

- S03 为只读查询模块；数量改变由 S04、S05、S07 办理。
- 返回产品身份分组及其每种包装规格的每件个数、总整件、总散个和仓库货位明细；各包装规格分别统计，不相互合并。
- 关键词和仓库控件、显示字段、展开行为及业务入口以 Demo 为准。仓库筛选目前筛选匹配规格，行总量仍是该规格跨全部货位的总量；不静默改为单仓合计。
- 库存为零仍是有效数据；空列表、零库存、请求未完成与查询失败应有可区分的展示状态。
- 业务成功后刷新受影响查询结果；正在显示的旧库存不是后端校验依据。
- 正式前端可复用展示组件，但两端查询必须经过各自身份边界。

### Testing Decisions

- 以页面查询与展开流程验证结果，复用 Demo 的库存和四种业务后查询先例。
- 每件 4 个的包装规格在 A 位为 3 件 1 个、B 位为 0 件 8 个时，该包装规格总量为 3 件 9 个，位置明细正确。
- 0 件 24 个不能自动显示为整件；同一产品身份的不同每件个数归组展示但数量不合并。
- 员工办理业务后，管理员另一个会话重新查询得到同一结果。
- 仓库及关键词筛选、无结果、服务失败和零库存分别验证；手机明细和业务按钮可用。

### Out of Scope

批次剩余量、金额统计、库存预警、统计看板、离线登记和单独的库存调整操作。

### Further Notes

依赖 S01、S02、S09；业务弹窗由 S04 负责。仓库筛选后总量含义是从 Demo 提取的当前契约，若后续要求单仓汇总需明确变更。

## S04 入库、出库、移动货位与拆件

### Problem Statement

人员需要登记四种日常库存业务，并保留实际发生时间。出库超量、移位只更新一边、拆件时自动改变包装状态或首次录入另设一套功能，都会使台账与现场不一致。

### Solution

两套系统使用 Demo 已有的四类业务弹窗。后端统一校验、原子保存库存变化和业务记录，首次手工录入使用入库，提交成功后前端才刷新结果。

### User Stories

1. 作为员工，我希望选择规格和货位登记入库，以便增加对应位置库存。
2. 作为管理员，我希望也能办理入库，以便不必切换员工系统。
3. 作为使用者，我希望首次手工录入库存使用入库，以便不重复学习初始化功能。
4. 作为使用者，我希望整件和散个分别录入，以便保留实际包装状态。
5. 作为使用者，我希望负数、小数和零变动被拒绝，以便避免无效数量记录。
6. 作为使用者，我希望出库分别校验整件及散个，以便不透支货位。
7. 作为使用者，我希望库存不足时看到可用数量，以便修正或选择其他货位。
8. 作为使用者，我希望选择原货位与目标货位移位，以便整理位置。
9. 作为使用者，我希望移位同时完成扣减和增加，以便不会出现只扣不加。
10. 作为使用者，我希望没有第二货位时先得到新增货位提示，以便完整选择目标位置。
11. 作为使用者，我希望拆件前看到增加散个的预览，以便确认数量。
12. 作为使用者，我希望散个不足时自行先登记拆件，以便系统不默默改变包装状态。
13. 作为使用者，我希望填写实际发生时间，以便补录也能表达真实业务时间。
14. 作为使用者，我希望可填写备注而不填来源、去向，以便符合已确认的简单业务范围。
15. 作为使用者，我希望取消弹窗不产生业务，以便错误选择不会改变库存。
16. 作为使用者，我希望失败保留输入，成功留下操作人和来源系统，以便继续操作并追溯。
17. 作为多人使用的团队，我希望竞争同一份库存也不透支，以便双方记录可信。

### Implementation Decisions

- 入库、出库与移位输入为产品包装规格、货位、整件数、散个数、实际发生时间和备注；移位增加目标货位。拆件输入拆开件数，并由所选包装规格取得每件个数。
- 入库增加指定货位；出库分别扣减整件和散个；移位在同一提交中扣原位、增目标位，总整件与散个均不变。
- 入库、出库、移位、拆件均明确选择对应每件个数的包装规格；拆件扣减整件，增加“拆开件数 × 每件个数”的散个。不能在出库时自动拆件，也不能把散个自动包装成整件。
- 普通数量为非负整数，至少一个数量大于零；拆开件数为正整数且不超过可用整件；移位两货位不同且都属于所选规格。
- 用户可填写实际发生时间，登记时间由后端产生。账号和来源系统由 S01 会话决定，不接受冒用。
- 首次手工录入仍产生入库记录，可备注说明；不提供直接覆盖库存、盘点或手工初始化入口。
- 事务、并发控制和幂等由 S09 承接；S04 定义单笔业务的数量效果和错误含义。失败不产生部分库存或业务记录。

### Testing Decisions

- 首选“从库存页进入弹窗 → 提交 → 展开货位 → 查看业务历史”的外部流程；复用 Demo 四类业务及超量拦截先例。
- A 位 3 件 1 个，每件 4 个：拆 1 件后为 2 件 5 个；再出 0 件 3 个后为 2 件 2 个。
- A 位 3 件 1 个、B 位 0 件 8 个：移动 1 件 1 个后 A 为 2 件 0 个、B 为 1 件 9 个，总量仍为 3 件 9 个。
- 出库任一单位不足均失败；不能用另一货位或等价个数绕过校验。相同原目标货位及无有效目标时拒绝移位。
- 取消与失败无数据变动；成功后有实际时间、登记时间、可信操作人和来源系统。
- 在后端 HTTP 入口配真实 PostgreSQL 验证并发出库与重复提交，不能只凭页面提示判断库存安全。

### Out of Scope

盘点、盘盈盘亏、报损报废、采购销售、来源去向、入库批次剩余量、自动拆包装和手工库存覆盖。

### Further Notes

依赖 S01、S02、S03 与 S09；S05 展示和更正业务，S08 展示系统操作日志。历史补录的时间顺序策略需与 S05 一并确认，当前时间预填不代表历史一致性问题已经解决。

## S05 业务历史与记录更正

### Problem Statement

员工和管理员需要共同查询库存业务，并修正登记错误。如果修改只更新记录文字、重复应用库存效果或丢失原内容，就无法核对库存和责任。

### Solution

沿用 Demo 的库存业务记录页、更正弹窗和修改记录弹窗。两端可更正所有普通库存业务记录；后端保存前后快照、修改账号、来源系统和时间，并校验更正后的库存。

### User Stories

1. 作为员工，我希望查看两套系统产生的业务历史，以便了解库存变动。
2. 作为管理员，我希望按来源系统筛选，以便核对员工端和管理员端的业务。
3. 作为使用者，我希望按入库、出库、移位、拆件和初始库存分类查看，以便快速定位记录。
4. 作为使用者，我希望用关键词查询产品、规格、货位、备注或操作人，以便找到目标业务。
5. 作为使用者，我希望同时看到实际发生时间和登记时间，以便判断补录情况。
6. 作为使用者，我希望记录显示产品身份、每件个数、货位、变动及发生端，以便知道操作内容。
7. 作为员工，我希望更正其他员工或管理员的普通业务记录，以便及时修正错误。
8. 作为管理员，我希望同样能更正任何普通业务记录，以便协助核对。
9. 作为使用者，我希望更正前看到原记录摘要，以便避免改错记录。
10. 作为使用者，我希望更正数量、实际时间和备注，以便使用已有 Demo 表单完成修正。
11. 作为使用者，我希望更正后库存只反映新的业务效果，以便不会重复累加。
12. 作为使用者，我希望会造成不足或负库存的更正被拒绝，以便其他已登记业务不被破坏。
13. 作为使用者，我希望查看每次修改前后内容、修改人和时间，以便追溯。
14. 作为使用者，我希望取消或失败不会修改记录，以便修正可以放心尝试。
15. 作为使用者，我希望其他人已修改同一记录时有冲突反馈，以便不会覆盖别人的更正。

### Implementation Decisions

- 共享业务历史包括 Excel 初始库存、入库、出库、移位和拆件；原操作人及来源保留，更正操作另记修改人及来源。每条库存记录明确关联产品身份及对应每件个数。
- 页面保留 Demo 的类型按钮组、关键词、来源系统筛选和现有表格，不自行增加日期范围或独立货位筛选控件。
- 本轮更正表单范围为数量、实际时间、备注；规格与货位没有 Demo 编辑控件，作为待确认差异保留。
- 更正原子更新库存、业务记录及修改记录；业务效果依据旧记录撤销后采用新内容计算，但数据库不得暴露中间状态。
- 每次更正保存稳定的修改前后内容与账号标识，而不依赖当前名称反推历史。不得删除历史或覆盖修改记录。
- 防止旧版本覆盖新版本；采用版本或等效冲突识别，由 S09 提供事务与重试一致性。
- Demo 的 Excel 初始库存记录没有更正入口。原需求关于初始记录更正与历史时间顺序的边界需确认；暂不擅自增加入口或把现有算法认定为完整时序校验。

### Testing Decisions

- 复用 Demo“登记入库 → 更正 → 查看修改记录 → 回库存核对”的完整交互。
- 原库存 3 件，入库 2 件后 5 件；把该入库改为 1 件后应为 4 件，不能变为 6 件。
- 更正移位应同步校验两货位；更正拆件使用原记录每件个数；会造成负数则整笔失败。
- 员工可更正管理员记录，管理员可更正员工记录；原来源和操作人不被改写。
- 连续两次更正可查看两组前后内容；取消、冲突或失败不新增成功修改记录。
- 用真实 PostgreSQL 验证同时更正同一记录和失败回滚；历史时间顺序的完整预期在规则确认后补齐。

### Out of Scope

删除业务历史、删除修改历史、审批流、未经确认的规格货位更正字段，以及自定的历史时序重排规则。

### Further Notes

依赖 S03、S04、S09；S08 接收更正操作日志。规格货位更正、Excel 初始记录更正、历史补录时序是本规格的明确待确认项，不应直接标记为整份可无条件实施。

## S06 员工账号管理

### Problem Statement

管理员需要为员工建立独立账号并控制是否可使用系统。员工不能获得账号管理能力，停用操作也不能只是让列表换一个状态文字。

### Solution

在管理员系统保留 Demo 的员工账号页、新增账号弹窗及启用／停用操作；后端执行管理权限和账号状态校验，并关联可信操作日志。

### User Stories

1. 作为管理员，我希望查看姓名、账号、状态及创建日期，以便管理现有员工。
2. 作为管理员，我希望填写姓名与登录账号新增员工，以便给每人独立身份。
3. 作为管理员，我希望重复账号被拒绝，以便账号身份唯一。
4. 作为管理员，我希望不能把管理员账号创建成员工账号，以便两个系统身份保持清楚。
5. 作为管理员，我希望停用员工账号，以便停止其继续使用系统。
6. 作为管理员，我希望重新启用账号，以便恢复允许的工作身份。
7. 作为员工，我希望使用自己的账号登录员工系统，以便业务记录标明本人。
8. 作为停用账号的员工，我希望明确收到不能登录或提交的反馈，以便知道操作未成功。
9. 作为管理员，我希望新账号能按确定的方式取得密码，以便真正可用而非只出现在列表。
10. 作为管理员，我希望启停账号产生管理日志，以便追溯由谁在何时操作。
11. 作为员工，我希望无法通过直接请求调用账号管理，以便权限范围明确。

### Implementation Decisions

- 页面归管理员系统；员工无菜单，所有管理请求仍须后端管理员身份校验。
- 沿用 Demo 新增弹窗的姓名、账号两字段，列表保留状态及创建日期；不添加账号删除、重置密码或管理员管理页面。
- 账号状态持久保存；停用账号不能新登录，既有会话在之后受保护请求中也须受停用状态约束。
- 员工身份不允许冒用管理员身份，账号建立规则与 S01 独立认证契约一致。
- 正式系统不使用统一的 Demo 密码。员工账号创建时生成一次性临时密码，首次登录强制修改；临时密码仅在创建成功时展示给管理员交付。
- 新增及启停记录可信管理员账号与操作结果；密码不出现在日志和查询返回中。

### Testing Decisions

- 复用 Demo“管理员新增员工 → 退出 → 新员工登录 → 管理员停用 → 再登录失败”的流程。
- 验证重复账号、管理员账号误作员工账号、空姓名账号的拒绝与表单输入保留。
- 停用前已登录的员工再次提交库存业务必须失败；不能仅测试新登录失败。
- 员工绕过 UI 调用新增、启停请求仍被拒绝，且数据库账号及库存不改变。
- 新增与启停在重启后保留，管理员日志可定位操作账号与时间。

### Out of Scope

多级角色、自助注册、账号删除、密码重置页面、员工考勤和人事管理。

### Further Notes

依赖 S01、S09；系统操作日志由 S08 展示。初始凭据规则已确认：创建时生成一次性临时密码，员工首次登录强制修改；不能把 Demo 的 demo123 当成正式凭据。

## S07 初始库存 Excel 导入

### Problem Statement

旧台账含缺项、单位不明、混合数量写法及疑似重复，不能直接转为库存。导入如果猜测单位、自动合并或覆盖已有库存，会破坏已核对数据。

### Solution

管理员选择整理后的 .xlsx、.xls 或 .csv 文件并预览、提交。问题行应在源文件中修正后重新上传；正式后端校验整批数据并持久保存。管理员可持续分批导入，不设置完成初始化或关闭导入动作。

### User Stories

1. 作为管理员，我希望独立进入初始库存导入页，以便员工不能误做批量导入。
2. 作为管理员，我希望选择整理后的库存模板并看到文件名，以便确认处理对象。
3. 作为管理员，我希望真实解析文件内容，以便预览不再使用模拟记录。
4. 作为管理员，我希望看到原行号和字段原值，以便回到旧台账核对。
5. 作为管理员，我希望产品身份、每件个数、仓库和货位的字段问题有具体提示，以便修正源文件后重传。
6. 作为管理员，我希望单位不明的数量停留在待核对状态，以便系统不猜件或个。
7. 作为管理员，我希望商品类别、类别名称和备注分别保留，以便原台账信息不丢失。
8. 作为管理员，我希望空白数量和已确认零数量区分，以便不把未知库存当成没有库存。
9. 作为管理员，我希望预览能定位文件中的行，以便回到原文件修正。
10. 作为管理员，我希望同一产品身份的不同每件个数分别导入和记账，以便支持多种包装规格。
11. 作为管理员，我希望同一产品包装规格可在不同货位分别导入，以便支持真实分放。
12. 作为管理员，我希望问题未处理完时不能提交，以便整批结果可信。
13. 作为管理员，我希望整批提交失败时保留文件与核对内容，以便重试不重复登记。
14. 作为管理员，我希望可按需继续导入新批次，以便逐步登记现有库存。
15. 作为员工，我希望首次手工录入仍通过入库，以便没有重复的手工初始化功能。
16. 作为使用者，我希望已有手工入库和业务历史不会被导入清空，以便真实记录保留。

### Implementation Decisions

- 文件字段为产品名称、规格、材质、颜色、每件个数、商品类别、类别名称、备注、仓库、货位、整件数、散个数；另保留原行号、原值、核对结果及问题说明。格式支持 .xlsx、.xls、.csv。
- 旧台账按需求文档 A 至 F 列映射整理，不能直接猜规格或单位。原表只用于参照，不修改源文件。
- 预览不写库存；缺必需列、未知含义列、缺项和无效数量等阻止项须按已确认规则解决，才可整批提交。产品身份字段必填及空值规则仍待确认。
- 问题行须由管理员修正源文件后重新上传；不在预览中编辑或排除问题行。
- 产品名称、规格、材质和颜色相同的记录属于同一产品；每件个数不同则对应不同包装规格，分别记账。产品身份字段的必填及空值判定仍待确认。
- 已有手工入库或既往导入记录不阻止新批次；新数量加入相应产品包装规格和货位库存。该规则按每件个数分别应用。
- 同一导入文件内完全重复行的处置仍待确认；实现不能自行选择累加、排除或拒绝。
- 整批提交以事务保存匹配资料、初始库存记录、数量及批次；不得采用 Demo 清空全部库存和业务历史的模拟替换方式。
- 管理员可持续分批导入；导入不设置完成动作，也不会关闭入口。

### Testing Decisions

- 使用真实的 .xlsx、.xls、.csv 文件验证“选择文件 → 预览 → 核对 → 提交”，管理员可在批次后再次导入。
- 缺列、缺字段、未知单位、负数小数及无效包装数量均能定位原行；确认前数据库库存不变。
- 空白数量与 0 分开处理；原始字符串保留；商品类别、类别名称、备注不会互相覆盖。
- 同一产品身份下每件 4 个与每件 6 个分别形成包装规格并归组展示；分别核对各包装数量在不同货位的库存。
- 批次仍有阻止项则整批拒绝；模拟提交失败不留下部分资料或库存，重试只产生一次成功结果。
- 已有手工入库或先前导入记录不拒绝新批次；确认提交后新数量加入对应库存，不清空原有业务历史。
- 员工直接调用导入请求被拒绝；导入批次之间入口持续可用。

### Out of Scope

历史库存流水导入、后续批量更新、直接上传未整理旧台账后自动推断、自动归并重复，以及独立手工初始化页面。

### Further Notes

依赖 S01、S02、S04、S09；S05 展示初始库存记录，S08 展示导入操作。格式及问题行修正方式、跨批次累加和持续导入已确认；产品身份字段的必填与空值规则、同文件完全重复行的处置仍待确认。原台账扫描数量是需求文档已有记录，本次未重新扫描 Excel。

## S08 系统操作日志

### Problem Statement

管理员需要知道员工进行了哪些操作；只显示管理员端自己的日志无法满足监督和核对。日志若没有操作账号或来源，无法区分同名人员及两个系统。

### Solution

沿用 Demo 系统操作日志页面。管理员默认查询管理员和员工两端记录，支持来源系统、操作人及关键词筛选；员工只查询员工端日志。库存业务历史继续使用独立页面。

### User Stories

1. 作为管理员，我希望默认看到两端的操作日志，以便核对员工工作。
2. 作为管理员，我希望只看员工端记录，以便定位员工操作。
3. 作为管理员，我希望只看管理员端记录，以便核对管理动作。
4. 作为管理员，我希望按操作人筛选，以便查看指定人员。
5. 作为管理员，我希望按账号搜索，以便区分同名人员。
6. 作为管理员，我希望按操作内容搜索，以便找到入库或账号启停等操作。
7. 作为使用者，我希望每条显示操作内容、操作人、账号、来源和时间，以便完整定位。
8. 作为管理员，我希望员工办理入库后能看到对应日志，以便核实其来源。
9. 作为员工，我希望只查看员工系统日志，以便不会取得管理员端日志。
10. 作为使用者，我希望登录、退出、资料维护和业务更正等被记录，以便不只有数量变动可追溯。
11. 作为使用者，我希望日志与业务记录能关联，以便进一步查看数量和修改详情。
12. 作为使用者，我希望筛选无结果有提示，以便知道查询确实完成。
13. 作为使用者，我希望退出并切换系统后筛选重置，以便不会沿用上一入口的条件。

### Implementation Decisions

- 日志保存稳定的操作人身份、当时账号及展示姓名、来源系统、操作内容、时间，以及可用的关联业务标识；不能只在查询时按当前姓名猜账号。
- 管理员查询范围为两端；员工范围为员工端。员工篡改来源筛选或直接请求管理员日志，后端仍必须限制返回范围。
- 沿用 Demo 的关键词、操作人选择框和管理员专有来源系统选择框，不添加日期范围或日志导出控件。
- S01、S02、S04、S05、S06、S07 提供可信操作事件；S08 负责查询和展示，不重复实现这些业务。
- 成功变更与相应日志必须有一致的保存结果；失败不能出现表示已成功变更的日志。密码、会话密钥和敏感凭据不能写入日志。
- 库存历史保留实际发生时间，系统日志使用系统操作时间；两个概念不能混淆。
- 员工当前可查看员工端其他员工日志，符合现有 Demo；是否进一步限制为本人属于后续变更，本轮不自行收紧。

### Testing Decisions

- 复用 Demo“员工登记入库 → 退出 → 管理员登录 → 查看及筛选员工日志”的流程。
- 管理员默认看到两端来源；按员工系统或管理员系统筛选后结果只含对应来源。
- 按操作人和账号搜索得到准确记录；组合查询、无结果、切换系统后条件重置均可用。
- 员工通过页面及直接 HTTP 请求均得不到管理员日志；可见范围不能仅靠客户端过滤。
- 检查日志显示的账号、来源和时间来自可信操作；账号名称改变后旧日志仍可识别原操作。
- PostgreSQL 重启后日志保留；关联业务成功、失败及回滚不会留下矛盾的成功日志。

### Out of Scope

日志删除、日志导出页面、复杂审计报表、管理员端日志向员工开放，以及用系统日志替代业务历史。

### Further Notes

依赖 S01、S09 并接收其他业务模块的事件。用户已经明确要求管理员可查看员工操作日志，此规则优先于早期“各自只查本端”的表述。

<a id="s09"></a>

## S09 共享持久化、并发与运行保障

### Problem Statement

正式系统需要多人在电脑和手机上操作同一库存。Demo 的内存数据、刷新复原和单页面模拟不能保证持久保存、竞争库存或失败恢复。

### Solution

采用 PostgreSQL 保存共享业务数据，同一 Monorepo 中的 `apps/api` 使用 Next.js 向 `apps/admin`、`apps/employee` 提供受保护的 HTTP 业务入口；以事务、幂等及冲突识别保证数量与记录一致，并在正式运行前验证备份恢复与多人访问。

### User Stories

1. 作为使用者，我希望刷新后数据保留，以便登记不是临时演示。
2. 作为管理员，我希望员工与管理员读写同一份数据，以便无需手工同步。
3. 作为手机使用者，我希望外出能通过自己的账号查询，以便了解当前库存。
4. 作为两名同时操作的员工，我希望竞争库存不会透支，以便台账可信。
5. 作为使用者，我希望同一笔业务重复点击不重复增减，以便不因操作习惯出错。
6. 作为使用者，我希望网络超时后重试能识别已提交业务，以便不出现两条记录。
7. 作为使用者，我希望提交失败不会只改一半数据，以便库存和记录一致。
8. 作为使用者，我希望网络失败保留输入并明确未登记，以便继续核对。
9. 作为使用者，我希望另一个会话看到已成功提交的结果，以便共用实时台账。
10. 作为管理员，我希望数据库或后端重启后可继续查询，以便系统可恢复。
11. 作为管理员，我希望更正冲突有明确反馈，以便不覆盖他人修改。
12. 作为管理员，我希望数据库可备份并实际恢复，以便意外损坏可处理。
13. 作为项目负责人，我希望部署费用先明确，以便决定正式运行环境。
14. 作为维护人员，我希望数据库变更可追踪与验证，以便升级不破坏已有台账。
15. 作为使用者，我希望数据库错误不会暴露技术凭据，以便系统信息安全。

### Implementation Decisions

- 唯一数据库技术选择为 PostgreSQL；开发的真实数据库集成测试也使用 PostgreSQL，不以 SQLite 的结果代替事务与并发验收。
- 数据基础覆盖账号、会话、规格、仓库货位、规格货位库存、业务记录、修改记录、导入批次、初始化状态和操作日志；保留稳定关联和历史快照。
- `apps/api` 使用 Next.js 运行后端 HTTP 入口；`apps/admin` 和 `apps/employee` 两个 React＋Vite 前端仅通过受保护接口访问数据。三个应用同仓库管理、各自构建，可通过同一外部入口提供访问。
- 两端的库存请求在各自身份校验后进入同一个后端业务模块；数据库连接配置和迁移只由 `apps/api` 管理，不按系统复制数据库、库存表或迁移目录。
- 事务与受影响库存的竞争控制保证原子更新；具体锁、版本及隔离方式在实施设计中选择，但必须通过真实并发验收。
- 每笔写操作有可识别的提交身份；同一身份同内容重试返回原结果而不再次应用，不同内容复用同一身份应报冲突。不能只禁用前端按钮。
- 业务账号、来源与权限基于会话；库存可用量在事务提交边界重新校验，不能使用客户端缓存数量。
- 数据库约束、迁移与一致性检查支持数量、关联及唯一性规则；历史时序的业务判定由 S04、S05 确认，本模块不自行补定。
- 业务和所需成功日志应一致保存；失败保持可重试信息但不显示成功。备份需包含所有相关业务数据，恢复需验证关联与库存。
- 运维配置、数据库凭据与前端可见配置分开；部署方式、数据库版本、ORM、备份频率、容量和费用暂不虚构。

### Testing Decisions

- 主要以真实 HTTP 业务请求和 PostgreSQL 集成结果验收；不逐个测试内部存储函数代替外部结果。
- 一个货位仅有 1 个散个时，两名员工同时各出 1 个：至多一笔成功，库存不负，业务和日志数量与成功笔数一致。
- 同一笔入库重复点击、超时重试或重复请求：库存增加一次、业务记录一次；复用提交身份但修改数量时报冲突。
- 移位中途失败不能只扣原位，更正及整批导入失败不能留下部分记录。
- 提交成功后另一会话刷新查询可见；刷新、后端重启或数据库重启后已提交数据不丢失。
- 从管理员应用提交入库，再从员工应用刷新查询，读取同一笔已保存的库存及业务记录；反向流程同样成立。两端各自提交的来源系统和操作账号能在管理员日志中核对。
- 旧版本并发更正同一记录不能覆盖新版本；明确返回冲突并允许重新查看。
- 执行一次备份恢复演练，核对库存、业务、修改记录、账号及初始化状态，不以生成备份文件作为恢复成功。
- 外网部署前验证两类真实账号在电脑和手机访问同一数据；费用和部署方式确认前不发布生产环境。

### Out of Scope

SQLite 兼容分支、离线写入、多主数据库、跨地域复制、未确认的容量承诺，以及本次规格编写期间的云资源开通或付费部署。

### Further Notes

本规格先提供数据基础，最后完成跨模块验收，不能放到所有业务实现之后才启动。S04、S05、S07 负责业务效果，本规格负责在真实数据库及并发下保障这些效果成立。

## 附录：正式系统技术选型 ADR

日期：2026-10-11。

### 状态

用户已明确技术栈、PostgreSQL 选择及 Monorepo 代码组织方式。本 ADR 记录正式系统的技术方向与应用边界，本次只编写规格，没有创建正式应用或迁移数据库。

### 背景

目前已有可双击打开的原生 HTML、CSS、JavaScript Demo。用户指定正式前端使用 React、后端使用 Next.js、以 Vite 为基座、数据库使用 PostgreSQL；前端页面以当前纯静态 Demo 为准。

### 决定

- 当前 Demo 继续作为独立的纯静态界面依据，保留不依赖服务的查看方式。
- 正式前端在 `apps/admin`、`apps/employee` 分别采用 React＋Vite，复现 Demo 的两套系统入口、导航、布局、字段与交互；管理员和员工是两个独立前端应用。
- 正式后端在 `apps/api` 采用 Next.js，在 Node.js 上提供 HTTP API，执行真实认证、权限、库存业务校验、事务与日志保存。
- Vite 承担前端开发及构建；Next.js 后端采用自身构建与运行流程，不把两个构建器合成一个构建链。
- PostgreSQL 保存共享数据；数据库集成及并发验收也使用 PostgreSQL。用户最新选择已明确，本轮不实施 SQLite 分支。
- 正式代码必须采用同一 Git 仓库内的 Monorepo：两个前端、一个共用后端。沿用 npm workspaces 管理 `apps/*` 和按需建立的 `packages/*`，三个应用各自构建。
- 两端可复用通用展示组件和接口契约，但保留独立登录、会话校验和功能导航；后端共用业务模块及一套 PostgreSQL 数据，数据库迁移集中在 `apps/api/db/migrations`。
- 前后端可通过统一外部入口提供访问，但浏览器只能通过后端接口访问数据。`prototype` 和双击 HTML 保持静态页面基准用途，不迁移成正式应用。

### 影响

前端技术改变不等于重新设计页面。Demo 的模拟账号、内存数据与假导入不能成为正式实现；正式系统需要Next.js 后端及 PostgreSQL 服务，双击文件仅用于 Demo 查看。数据库版本、ORM、部署方式、费用及备份频率尚未确定。

这是根据用户组合选型形成的应用拆分，后续实施前应锁定兼容版本。Next.js 请求处理及构建能力、Vite 的 React 模板分别见 [Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)、[Next.js CLI](https://nextjs.org/docs/app/api-reference/cli/next)、[Vite 指南](https://vite.dev/guide/)。
